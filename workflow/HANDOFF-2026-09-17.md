## 5. Hard-won findings — the expensive ones

### 5.1 📱 iOS gives a home-screen app storage completely separate from Safari

Session, cookies, localStorage, IndexedDB **and the service worker** are all isolated.
A magic link **always** opens in Safari, so it signs *Safari* in and leaves the installed
app logged out **forever**. No redirect crosses that boundary.

The app therefore sends one `/auth/v1/otp` request that produces **both** a link and a
code, and the phone flow types the code into an overlay in the same document.

⚠ **This is why the Magic Link email template must contain `{{ .Token }}`.** If someone
"tidies" that template back to the default, phone sign-in breaks with no error that
points at the cause.

⚠ **Corollary XENO should be told once in the UI:** installed app, Safari tab and desktop
are **three separate sessions**, each needing its own sign-in.

### 5.1b ⚠⚠ THE WORST BUG SO FAR — the app could not update itself

Found 2026-09-17, after XENO reported that a deployed fix "didn't show up" on desktop
even after a hard refresh. Two compounding defects, both mine:

1. **`isBusy()` counted "the caret is inside a `.txt`" as busy.** A notes app focuses its
   editor at boot — `startApp()` does it deliberately — so **busy() was true from launch,
   forever**. The idle gate never opened, the handover was never requested, the waiting
   worker never activated.
2. **`pendingSaves` was a counter and it leaked.** Every keystroke called `persist()`,
   which cleared the previous debounce timer and set a new one — so N keystrokes
   incremented N times while only the LAST timer fired and decremented once. The counter
   ratcheted up and never came back to zero. A counter was the wrong shape; it is now one
   flag per pane.

**Why this was so hard to see from the outside:** the deploy was live, the files on the
server were correct, and a hard refresh appeared to do nothing — because a precache-first
worker keeps serving its build until something tells it to step aside, and nothing ever
did. It looks exactly like a caching bug and it is not one. I only found it by driving a
real drag against the production URL, confirming the NEW code was live and behaving
correctly, and then asking why the browser was not running it.

**This is the exact failure `ONESHOT-WEBAPP.md` §7.4 warns about**, which I wrote, and
then walked into four days later. The rule says *enumerate what a reload would destroy*.
A caret POSITION is destroyed by any reload anyway and is cheap. Unsaved edits, live
gestures and an in-progress selection are what is expensive.

**Now guarded by four assertions in `app.test.mjs`:** idle with the caret parked in the
editor · busy immediately after a keystroke · idle again 1.5s after typing stops · busy
while a selection is live. **Do not delete these.** An app that can never report itself
idle can never take a new build, and nothing else in the suite would notice.

Also added a **safety valve** in `update.js`: if an update has been waiting more than five
minutes, the next time the document is hidden it applies regardless of `busy()`. §7.6 says
wait indefinitely, and that is right while someone is looking — but an update waiting
against a `busy()` that never clears is an update that is never arriving, and hidden means
nobody is watching.

### 5.2 📱 Bugs found by tests that no amount of reading would have caught

1. **`store.js` returned the raw `IDBRequest`** instead of `.result` for a missing key. A request object is truthy, so *"no session stored"* read as *"signed in"* and the app skipped the sign-in gate entirely. Needed a real IndexedDB to find.
2. **`getPropertyValue` on a `calc()` custom property returns the unresolved token stream**, so `parseFloat('--bar-h')` was 0 — in shipped code, not just the test. **Never parse a calc() custom property. Measure the element.**
3. **The lexical guards fired on my own explanatory comments**, because the comments name every forbidden string. Strip comments *first*. This is the source document's own lesson and I needed it within a minute of writing the test.
4. **The peek created an overlap where two grab strips share pixels** and DOM order decides the hit test, so "left means back, right means forward" fired **the wrong direction at exactly the tapped pixel**. Rule restated per-pane.

### 5.3 ⚠ Security findings

- **`postgres_changes` does not apply RLS to DELETEs.** With `replica identity full`, deleting a note broadcasts the **entire row to every subscriber of that table**. This is a primary reason for the broadcast decision.
- **`postgres_changes` would require `GRANT SELECT` on `notes.*` to `authenticated` project-wide** — widening exactly the surface the dedicated schema exists to protect.
- **`sb_*` keys are silently ignored as a Realtime `access_token`.** Fine as the `apikey` query param; not a JWT.
- **`you.github.io` is ONE origin for every repo that account publishes.** localStorage, IndexedDB, CacheStorage and the SW registration list are shared across all of them. Path buys scope, never storage. **Namespace every storage key.** An unfiltered `caches.keys()` sweep is cross-project destruction.

## 6. Live sync — designed, not built

**Decision: broadcast from the database.** A `SECURITY DEFINER` trigger calls
`realtime.send()` on topic `notes:<user_id>` with a thin `{op, id, updated_at, origin}`;
the device pulls the row over PostgREST it already has.

Why not `postgres_changes`: the grant widening (§5.3), the silent 1 MB payload cliff
that mangles rather than drops rows, and the DELETE/RLS hole. Supabase's own guidance is
*"don't use postgres_changes for new applications."*

**Full verified wire protocol is in `projects/notes-app/REALTIME-FINDINGS.md`** —
`vsn=1.0.0` object envelopes, Phoenix protocol, 25s heartbeat, the `access_token` refresh
message, join payload shapes, every documented error code. Two items are flagged
⚠ UNVERIFIED in that file: the argument order of `realtime.send` (the docs and Supabase's
own prompt file contradict each other) and the payload shape of `realtime.broadcast_changes`.
**Confirm the first with:**

```sql
select pg_get_function_arguments(oid) from pg_proc
 where proname in ('send','broadcast_changes') and pronamespace = 'realtime'::regnamespace;
```

**Design consequences that are easy to miss:**
- Delivery is **at-most-once**. The stream is a latency reducer, never the record — exactly the rule `PROTOCOL.md` already states about messaging. Reconcile on reconnect; keep poll-on-focus as the floor.
- **Self-echo is not optional to handle.** A database-originated broadcast always reaches the writer. Without an `origin` field you get an echo loop the moment a remote apply re-triggers a local write.
- **A dead socket on iOS stays `readyState === 1` indefinitely.** Track the outstanding heartbeat ref and force-close yourself. This is the single most important piece in a PWA.
